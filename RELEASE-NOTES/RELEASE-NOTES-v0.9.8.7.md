# ZTHL Aegis v0.9.8.7 — 发布说明

> 2026-11-08。本版是 v0.9.8.6 的**并发公式实机校正版**：408 公式原式在本机 WSL 切片
> （5 核 / 5GB）上机验证时会把 accept 默认并发压成 1（串行），与同环境实测 plateau（4–8）
> 反证；本版按实测重标定并补回归臂。不改 WSL 资源上限配置（见 §4）。

## 1. 为什么发这一版

v0.9.8.6 首次把 408 安全并发公式落进 `gk_hub_scheduler.adaptive_workers`。上机验证
（非纸面推演）发现：

- 本机 WSL 实际是 `.wslconfig` 的 **processors=5 / memory=5GB** 切片：`visible_cpus()=5`、
  空闲内存 ≈4.5GB；
- 408 原式 `W=min((C-4)/(1+f), 0.6R/(180+60f), 80/(1+f), 8)` 在该切片给出 f=1 → 1、
  f=2 → 1、f=3 → 1；
- 同环境实测：重活四文件 n=1 59.0s / n=2 53.0s / n=4 49.5s / n=6 46.6s；全量
  n=8 211s / n=12 206s ⟹ plateau 4–8。原式与实测反证：会把 accept 从 8 并发压成串行。

## 2. 变更

| 文件 | 变更 |
|:--|:--|
| `scripts/gk_hub_scheduler.py` | 408 公式实机校正：① 4 核 OS 保留改为按切片比例 `r=min(4, max(1, C//4))`（宿主级预留不在 WSL/cgroup 切片里重复扣）；② 核项除数改 `max(1,f)`（第 1 个外部子进程按阻塞 I/O 计，f≥2 才线性计入 CPU）；③ 保留 ×2 I/O 超订（2026-09-24 实测）、内存项 `0.6R/(180+60f)`、进程预算 `80/(1+f)`、机器令牌 8 与 todo 收紧 |
| `scripts/test_gk_hub_scheduler.py` | 公式臂按实机锚重写：5 核 f=1→8 / f=2→4 / f=3→2；16 核 f=1..3→8；内存/进程/cap/todo 各自单独生效；f=0 旧口径逐位不变 |

## 3. 验证（含可复现数字）

- 实机读数（WSL，visible=5 / free≈4.5GB）：`[(f=0,4), (f=1,8), (f=2,4), (f=3,2)]`；
  accept 默认 f=1 ⟹ `JOBS=8`（与 v0.9.8.6 之前的默认一致，无退化）。
- `test_gk_hub_scheduler.py` + `test_gk_accept_cli.py`：**32 passed**。
- 公式各支路单测：内存 600MB/f=2 → 1；进程预算 f=40 → 1；cap=4 → 4；todo=3 → 3。

## 4. 明确不做

- **不改 `.wslconfig`**（`processors=5 / memory=5GB / swap=4GB`，2026-09-23 事故后护栏）：
  宿主 15.7GB 总内存、当前仅剩约 4GB 空闲，抬高 WSL 内存上限会把 `vmmemWSL` 峰值顶进
  宿主余量（蓝屏复现路径）；本机测试是 I/O-bound，5 核切片的实测 plateau 已由 8 worker
  达成，改核数收益不成立。
- 不采用 408 报告的档3 `-n 3` 推演值：该值来自事故后未实测的计划，本机实测重活 n=4–6
  安全且更快；公式校正后 f=3 仍收紧到 2。

## 5. 与 v0.9.8.6 的关系

v0.9.8.6 = 门禁漏洞 + 测试长尾修复（含 408 原式首版落地）。
v0.9.8.7 = 并发公式实机校正；功能行为与 .6 相同，仅调度标定不同。对外建议直接使用 v0.9.8.7。
