## 1. 五个阶段

1. **预检**：16 项检查全过才允许往下走；
2. **导出**：按排除面生成过滤快照（干净的单提交树，不带历史）；
3. **镜像**：整树同步到公开工作副本（多余的删掉，版本库目录永不动）；
4. **提交与双 tag**：公开仓提交，同一版本号在两仓各打一个带说明的 tag；
5. **推送与记账**：推送分支与 tag，并把「版本 ↔ 私仓提交 ↔ 公开提交 ↔ 导出文件数」写进账本。

## 2. 预检 16 项

| 类别 | 检查 |
|:--|:--|
| 打包 | 打包脚本参数契约、打包产物四件套（压缩包 / 校验和 / 清单 / 来源说明） |
| 文档 | 事实块一致、文档特性覆盖、文档对齐、裁决面清单无漂移、**机制正本无漂移** |
| 包 | 包完整性（命令/插件/钩子必须都有载体）、仓库索引无漂移、第三方件指纹 |
| CI | 最小权限、动作按 SHA 固定、`run` 注入面 |
| 发布 | 发布说明存在且措辞机检通过、上传件齐全、工作流路径契约 |
| 性能 | 基线新鲜度、三套基准回归 |

第 16 项 **`mechanism_docs`**（2026-11-16 新增）：登记在 `references/mechanism-registry.json`
的每个机制，其正本文档里的事实块必须与活代码一致（入口脚本 / 公开函数数 / CLI 入口 / 测试 /
校验命令，由 `scripts/gk_mechanism_docs.py --write` 生成）；`上一版..HEAD` 新增的机制脚本
必须登记，否则要么补正本、要么在登记表里写**带理由**的豁免。没有这道闸，新机制可以只进代码、
不进文档，文档面就重回「靠人记」。

判定纪律：

- **FAIL 才红**；SKIP 表示「当前树里该项不适用」（例如导出树没有 `docs/`）；
- **WARN 不判红**，但会打印原因——WARN 的语义是「已确认可接受 / 环境能力不足」；
- 依赖缺失（例如镜像里没有 YAML 解析库）记 WARN 跳过，**不算违规**。

## 3. 单向发布桥

- 方向唯一：私仓 → 公开仓；**绝不回灌**。
- 默认 dry-run，只有显式落刀才写；缺省不推。
- 拒绝条件（任一命中即零写）：版本号已存在于任一仓、公开副本有未提交改动、
  公开目录不是 git 仓或不在主分支、私仓不干净、版本说明缺失、远端不在允许清单。
- **没有 force push 路径**。
- 生成物与账本分离：账本在私仓 `docs/` 下，`docs/` 属导出排除面，不会外泄。

## 4. 发布说明的机检（C1–C5）

| 规则 | 内容 | 是否阻断 |
|:--|:--|:--|
| C1 | 公开面禁词（内部路径、真实账号、论文面标识） | 阻断 |
| C2 | 同一行混用「已完成」与「计划/草案」 | 阻断 |
| C3 | 提交主题覆盖度提示 | 仅提示 |
| C4 | **数字回环**：说明声明的「N 个提交」必须等于 `上一版..本版` 的实际提交数 | 阻断 |
| C5 | **安全锚点**：说明里的安全主张必须能在活代码里找到锚点 | 阻断 |

C4 是 2026-11-16 补的：此前数字靠手填，写错也能通过（首版把 260 写成 171）。
两条口径约定：

- 比较基准取**同名 tag**（发布口径 = tag 所指提交），避免说明写完后主干再提交造成假红；
- **只在私仓生效**：公开仓是过滤镜像，一次发布只产生一个提交，用它算提交数必然误判。

## 5. 导出树自洽

公开树没有 `docs/`，因此：

- 文档对齐检查在导出树里以「发布模式」运行，缺席的排除面文档记 SKIP；
- 裁决面清单在导出树内按导出集重新生成，避免「清单里有一堆不随包的文件」。

判据统一为「`docs/` 是否随包」，**不要用「有没有 `.git`」判断**——公开副本本身也是 git 仓。

## 6. 棘轮

- 内联脚本片段数量有硬上限（当前 88 条），只许调低；
- 需要新增片段时，先把等量的旧片段下沉到独立脚本或改用 shell 算术；
- 受保护区（门禁自身关键区段）不计入可改写范围，合并闸会校验其未缩水。

## 7. 常见故障

| 现象 | 根因 | 处置 |
|:--|:--|:--|
| 推送时弹密码框并挂住 | 子进程继承了编辑器设置的 `GIT_ASKPASS` | 桥内固定剔除 askpass 并设「无凭据立即失败」 |
| 打 tag 被拒（钩子报错） | Windows 上 `python3` 是商店占位别名，钩子解释器不可执行 | 钩子先验证解释器可执行再采纳 |
| 推送被拒（权限范围不足） | 令牌缺少工作流文件权限 | 给令牌补权限，或改用已授权的凭据源 |
| 版本已存在 | 重复发版 | 先确认是否为重建 tag 场景，再按纪律处理 |

## 8. 纪律

1. tag 只打在**干净的私仓主干**上；发版前先推主干，避免「tag 有了、分支落后」。
2. 账本只在私仓维护，不进公开包。
3. 重建 tag 属于发布面操作，须显式说明原因，并保证公开仓与私仓的 tag 同名同指向内容。
