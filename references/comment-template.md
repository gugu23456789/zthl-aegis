# 注释模板与写作规格（COMMENT-TEMPLATE）

> 适用：`scripts/*.py`、`scripts/*.sh`、根 `gatekeeper-cli.sh`、`install.sh` / `uninstall.sh`。
> 定位：**一份可复制的注释模板 + 可机检的写作规格 + 注释变迁的记账方式**。
> 本文所有比例来自 2026-11-10 对技能仓 762 个源码文件的实测（口径见 §8），不是估算。
> 机器可读骨架：`references/comment-templates.json`（登记表）+ `scripts/gk_comment_scaffold.py`（scaffold/check/promote）。

---

## 0. 结论先行

| 对象 | 行数 | 注释行 | 注释率（注释/总行） | 有效口径（注释/(注释+代码)） |
|:--|--:|--:|--:|--:|
| 全仓（762 文件，py/sh/ps1/mjs） | 211,622 | 42,035 | **19.9%** | 23.1% |
| Python（685 文件） | 192,026 | 36,969 | 19.3% | 22.6% |
| Shell（75 文件） | 19,509 | 5,059 | 25.9% | 27.4% |
| `gatekeeper-cli.sh`（单文件） | 12,767 | 4,060 | **31.8%** | 33.0% |

- **"大部分文件注释 50%" 不成立**：≥50% 的文件只有 4 个（3 个 50–70%，1 个 67.6%）；550 个文件落在 10–30%，103 个 <10%。
- **"gatekeeper.cli 注释特别多" 成立，但不是 50%**：31.8%，且它一个文件就占了全仓注释总量的 **9.7%**（4,060 / 42,035）。
- 观感被放大的原因：该文件**前 40 行有 29 行是注释（72.5%）**，加上 45 处 `# ───` 分节线和 7 个 `PROTECTED_REGION` 块，读起来像"半篇散文"。全仓注释块平均 2.3 行、中位数 1 行、最长 76 行。
- 形态上：80.6% 的注释块含中文散文，36.8% 含日期，19.5% 含工程编号，**同时具备"日期+编号+中文"的只有 13.7%**。编号和时间是**高价值但低频**的要素，不是每个注释都需要。

## 1. 注释的七种形态

现有注释不是一种文体，而是七种职责不同的"零件"。写之前先选形态，再套模板。

| # | 形态 | 作用 | 允许长度 | 真实样例 |
|:--|:--|:--|--:|:--|
| A | 文件头 Banner | 一句话定位 + 设计约束 + 阅读入口 | 3–10 行 | `gatekeeper-cli.sh:2-9` |
| B | 分节线 | 切分逻辑区块，给 grep/人眼定位 | 1 行 | `# ─── 允许的推送远端白名单 (F8.1 远端验证门禁) ───`（`gatekeeper-cli.sh:49`） |
| C | 锚点行 | 日期 + 工程编号 + 结论 + 净行数，供机检与追溯 | 1–3 行 | `gatekeeper-cli.sh:24` |
| D | 事故/决策复盘块 | 病灶 → 机理 → 正解 → 判据，防止后人回退 | 6–20 行 | `gatekeeper-cli.sh:87-95` |
| E | 接口契约 docstring | Usage / Exit / 参数单源 / 数据落点 | 10–40 行 | `scripts/gk_finding.py:2-39` |
| F | 行内 why | 解释反直觉的一行代码 | ≤1 行 | `# R2（2026-09-22）：state 序列化单一事实源 —— 勿再内联 json.dump 直写 state。`（`scripts/gk_finding.py:50`） |
| G | 标记 | 待办 / 风险 / 受保护区域，供机检扫描 | 1 行 | `# TODO(注入): ...`（`scripts/otd_probes.py:162`）、`# PROTECTED_REGION_START::constants`（`gatekeeper-cli.sh:12`） |

### 1.1 正确示例：锚点行（形态 C）

```bash
# 2026-09-24 XENV-FORM ECC-9D6B0291E793：WSL 形态同名派生（sed 表达式逐字复用同行 ...；**净 0 行**）
```

一个合格锚点行包含四段，缺一不可：

1. `YYYY-MM-DD` —— 变更发生日（不是写注释的"今天"）
2. 工程编号 —— `R7` / `R-16` / `ECO-*` / `ECC-*` / `W2A-*` / `F8.1`，且能在 finding 台账或计划文档里查到
3. 结论句 —— 这一行到底改了什么
4. 净行数 —— `**净 0 行**` / `+3 行` / `-12 行`，用于判断是否引入锚点漂移

### 1.2 正确示例：事故复盘块（形态 D）

```bash
# 事故（取证实测）：2026-09-15 13:53–13:54 一次**人工 J5 沙箱**用相对路径 `ln -s` 且 cwd=`/`
# 以 root 执行 ⟹ 沙箱建在**根目录** ⟹ SKILL_DIR 解析成 `/` ⟹ 域孪生与夹具全落根目录；
# 两天后这批残留被 hook 的就近 state 误领（F5 越界误伤）⟹ **范围外编辑被误 BLOCK**（现场实证）。
# 判据两条（fail-loud；软链可跟随 ⟹ 合法沙箱 = `scripts` 软链到真 scripts/，仍通过）：
#   ① 落在文件系统/挂载根 ⟹ 不可能是技能根；
#   ② 解析不到 `scripts/gk_state.py` ⟹ 疑自指软链 / 空沙箱。
```

这类块只允许写五件事：**何时、什么现象、根因、判据、怎么防**。不要写"请注意""务必小心"这类没有判据的情绪句。

## 2. 必要组成要素（最小集）

一个值得保留的注释，最少要有下面 5 个要素中的 **3 个**；锚点行（形态 C）必须 **5 个全有**。

| 要素 | 回答的问题 | 写法要求 | 例 |
|:--|:--|:--|:--|
| **锚 Anchor** | 这条注释属于哪次工程变更？ | `YYYY-MM-DD` + 工程编号，一行内 | `2026-11-01（开源可移植）` |
| **因 Why** | 不写会出什么事？ | 病灶/事故/反例，一句话说清后果 | `原写死两个本机组织的远端前缀 ⟹ 他人机器上 push 恒 remote_not_allowed` |
| **界 Boundary** | 边界在哪？失败怎么表现？ | 判据、白名单、`fail-loud` / `fail-closed`、`净 0 行` | `未知 host / 本地路径仍拒绝（F8.1 判据不变）` |
| **证 Evidence** | 凭什么这么说？ | 实测数字、耗时、用例名、`references/...md` | `3×/4× 仅 ≤9% 收益，且 JOBS=15 触发 1 例并行假阳性` |
| **变 Delta** | 改了几行？会不会漂移？ | `净 0 行` / `+N` / `-N`；追加式更正 | `**净 0 行**以免新增锚漂移` |

**明确不要求**：注释复述代码在做什么（`what`）、逐行翻译、完整调用栈。代码能自解释的部分，注释一律不写。

### 2.1 必写 / 禁写清单

**必写**

- 反直觉的实现（为什么不用更直观的写法）
- 安全边界与失败姿态（`fail-loud` / `fail-closed` / 静默的例外及其理由）
- 兼容性/双宿主形态（WSL / MSYS / Windows-python）
- 事故判据与现场证据
- 单一事实源（"唯一实现在这里，禁止第二实现"）
- 故意保留的"丑"代码（`shellcheck disable` 的理由）

**禁写**

- `# 设置变量`、`# 循环遍历` 这类 what 注释
- 无日期、无编号的"历史遗留"叙述
- 把 commit message 原样粘进文件
- 超过 20 行的单块散文；需要更长就拆成文档并在注释里给路径
- 已失效的锚点（编号在 finding 台账查不到，且未标 `[已归档]`）

## 3. 模板（可直接抄）

### 3.1 Shell 文件头

```bash
#!/bin/bash
# <文件名> — <一句话职责>（<首个工程编号>，YYYY-MM-DD；<裁定来源>）
# =============================================================================
# 痛点（实测）：<不解决会出什么事，带数字>
# 机理：<为什么会这样，一到两句>
# 正解：<本文件采用的策略；单一事实源在哪>
# 边界：<明确不做什么；失败姿态 fail-loud / fail-closed>
#
# Usage:
#   bash scripts/<name>.sh <必选> [--flag]
# Env: <变量名（默认值）> —— <作用>
# Exit: 0 = <语义>；1 = <语义>；2 = <语义>。
set -uo pipefail
```

### 3.2 锚点行（每处非平凡变更一行）

```bash
# YYYY-MM-DD <工程编号>：<改了什么>；<为什么必须这样>；**净 N 行**；证据：<路径/用例/实测数字>
```

### 3.3 事故复盘块

```bash
# 事故（<取证方式>）：YYYY-MM-DD <现象，带时间与现场>。
# 根因：<一句话>。
# 判据：① <可判定的条件>；② <可判定的条件>。
# 防线：<哪一行/哪个函数负责拦截；失败姿态>。
```

### 3.4 Python 函数/模块契约

```python
"""<symbol> — <一句话职责>（<工程编号>，YYYY-MM-DD）

契约:
  - 输入: <类型/形态/允许的边界>
  - 输出: <结构；stdout JSON 形态>
  - 失败: <异常/exit code；是否 fail-closed>

单一事实源: <哪个模块/函数>；禁止第二实现: <反例>。
变更:
  - YYYY-MM-DD <编号>: <结论>；净 N 行。
"""
```

### 3.5 行内 why

```python
# <编号>（YYYY-MM-DD）：<反直觉点> —— <不这么做会怎样>。
```

### 3.6 分节线

```bash
# ─── <区块名>（<编号/约束>）───
```

只用于单文件超过 ~300 行、且区块有独立契约的场景；不要给每 20 行都加一条。

### 3.7 变更记录（追加式，不改历史）

```bash
# 变更记录（append-only，旧行不改写）:
# - 2026-09-24 <编号>: <结论>；净 0 行。
# - 2026-10-29 复核: <新证据> ⟹ <结论是否修正>。
# - ⚠ 归因更正（2026-09-24，实测证伪）: 原注释称 "<旧结论>"，实测为 "<新结论>"。
```

### 3.8 标记

```bash
# TODO(<owner/触发条件>): <要做什么>；触发: <何时必须处理>；缺省风险: <不做的后果>
# WARN: <已知风险>；判据: <如何观测>
# PROTECTED_REGION_START::<区域名>
```

`TODO` 必须带 owner 或触发条件；裸 `TODO` 视为无效注释。

## 4. 注释比例预算

按本次实测分布定预算，目标是"注释多而不水"，不是追求百分比。

| 文件类型 | 建议区间 | 硬上限 | 依据 |
|:--|--:|--:|:--|
| 新增 Python 模块（非测试） | 15–30% | 40% | 全仓 py 主区间 10–30% |
| 新增 Shell 脚本 | 15–35% | 45% | 全仓 sh 均值 25.9% |
| 测试文件 | 5–20% | 30% | 测试靠用例名自解释，注释只写"为什么这么测" |
| `gatekeeper-cli.sh` | 25–35% | 40% | 现状 31.8%，已接近上限 |
| 单个注释块 | 1–6 行 | 20 行（事故块） | 全仓均值 2.3 行；≥20 行仅 17 块 |
| 文件前 40 行 | ≤25% | 40%（仅主 CLI banner 例外） | 全仓前 40 行均值 5.9% |

**计算口径**：`注释率 = 注释行 / 总行`（含空行）；跨文件比较时用 `有效口径 = 注释行 / (注释行 + 代码行)`。Python docstring 计入注释；Shell heredoc 正文既不算代码也不算注释。

## 5. 注释变迁历史怎么记

注释的价值在"可追溯"，不在"写得多"。变迁记录遵守三条：

1. **追加不改写**：旧结论保留，新结论另起一行；确需推翻时用 `⚠ 归因更正（date，依据）` 显式标注。
2. **锚点可反查**：注释里的工程编号必须能在 `docs/analysis/`、`references/` 或 finding 台账里找到对应记录；找不到的编号视为死锚。
3. **和 commit 对齐**：提交信息引用同一编号（`feat(R7.7): ...`、`fix(hook): ... ECC-xxxxxxxx`），注释与 commit 互为索引。

跨文件的宏观变迁（谁在何时改了什么、净行数多少）统一落到 `docs/analysis/YYYY-MM-DD-<topic>.md`，格式沿用 `docs/analysis/commit-evolution-20261002.md`：

```
<sha> YYYY-MM-DD <type(scope)>: <结论>（<编号>）
```

文件内只保留"与本文件行为相关"的那一条锚，不复制整张 changelog。

## 6. 机检规则建议

若后续要落成 lint（建议命名 `scripts/gk_comment_lint.py`，本次不新建）：

| 规则 | 判据 | 级别 |
|:--|:--|:--|
| 锚点日期合法 | 注释含 `20\d{2}-\d{2}-\d{2}` 且 ≤ 今天 | ERROR |
| 锚点编号可查 | `R\d+` / `ECO-*` / `ECC-*` / `F\d` 能在台账或 docs 命中 | WARN |
| 裸 TODO | `# TODO` 后无 `(` 或无触发条件 | WARN |
| 注释块过长 | 单块 > 20 行且不含事故关键词（事故/根因/判据） | WARN |
| what 注释 | 匹配 `^\s*#\s*(设置|遍历|循环|定义|返回|获取)\b` | INFO |
| 比例越界 | 单文件注释率 > 40%（测试 > 30%） | WARN |
| 空泛断言 | 含"注意/务必/小心"但无判据/数字/路径 | INFO |

机检只读、默认 `WARN`，不得因为注释不合规阻断代码路径。

## 7. 反模式（本仓真实存在，需逐步收敛）

1. **散文膨胀**：单块 76 行的历史叙述（全仓仅 17 块 ≥20 行，但都在核心文件里）。→ 拆到 `docs/analysis/`，注释只留锚 + 一句结论 + 路径。
2. **同一事实源写两遍**：注释里重复描述另一文件已定义的契约。→ 改为"单一事实源 = `scripts/xxx.py`，禁止第二实现"。
3. **编号通胀**：`P1/P2/C1/F1/R1` 这类短编号在 42,035 行注释里出现数千次，跨文件歧义。→ 短编号必须带文件名或长编号消歧。
4. **过期锚**：注释引用的 finding 已关闭/归档，但注释仍写成"现行"。→ 归档时补 `[已归档 YYYY-MM-DD]`。
5. **只写 what**：`# 读取配置`、`# 返回结果`。→ 删除。
6. **head 区过重**：文件前 40 行 72.5% 是注释，真正的 `set`/常量被推到第 10 行之后。→ Banner 压到 ≤10 行，细节下沉到函数契约。
